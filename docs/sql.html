Integer arithmetic that overflows is an error (22003). Division by zero is 22012. Date and time arithmetic that leaves the representable range (a timestamp or date plus an interval, an interval sum or product whose months, days or time no longer fit) is an error too (22008).

Auto-incrementing columns

SERIAL, BIGSERIAL, SMALLSERIAL and the standard GENERATED { ALWAYS | BY DEFAULT } AS IDENTITY all create a column backed by its own sequence (<table>_<column>_seq). An omitted value takes the next number; the column is implicitly NOT NULL.

sql
CREATE TABLE tickets (
  id   BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  note TEXT
);
INSERT INTO tickets (note) VALUES ('first'), ('second') RETURNING id;
--  id
-- ----
--   1
--   2

SELECT now()                                   AS instant,
       date_trunc('month', DATE '2026-08-30')  AS month_start,
       EXTRACT(dow FROM DATE '2026-08-30')     AS day_of_week,
       DATE '2026-08-30' + INTERVAL '10 days'  AS later,

       to_char(now(), 'YYYY-MM-DD HH24:MI')    AS formatted;

An interval literal counts any of year, month, week, day, hour, minute, second, millisecond (ms, msec) and microsecond (us, usec), singular or plural, and an HH:MM:SS clock. A time may give its hour with one digit (TIME '3:16:17'). A DATE read from text that also carries a time of day ('2024-01-01 10:00') keeps the date part.

Date and time arithmetic:

ExpressionResult
date + integer, date - integerDATE, whole days later or earlier
date - dateINTEGER, the number of days between
date + timeTIMESTAMP at that time of day
date + interval, timestamp + intervalTIMESTAMP (a TIMESTAMPTZ stays one)
timestamp - timestampINTERVAL
time + interval, time - intervalTIME, wrapping around midnight
interval * number, interval / numberINTERVAL

Multiplying or dividing an interval by a fractional number carries the fractions down: the months truncate toward zero and the fractional month becomes days at 30 days per month, the days truncate and the fractional day becomes time at 24 hours per day, and the time rounds to the microsecond. Nothing carries upward. So INTERVAL '1 mon' * 1.5 is 1 mon 15 days, INTERVAL '1 day' / 3 is 08:00:00, and INTERVAL '23:59:59' * 2 is 47:59:58. sum adds intervals field by field, and avg divides that sum by the count with the same carry.

DATE, TIMESTAMP and TIMESTAMPTZ mix without a cast. A DATE becomes a TIMESTAMP at midnight, and a DATE or TIMESTAMP becomes a TIMESTAMPTZ read in the session time zone, wherever two of them meet: comparisons, BETWEEN, IN, CASE, COALESCE, NULLIF, greatest / least, ARRAY[...], VALUES and UNION / INTERSECT / EXCEPT. So COALESCE(max(ts), CURRENT_TIMESTAMP) is a TIMESTAMPTZ, and ts BETWEEN $1 AND $2 takes DATE bounds as midnight.

The session time zone defaults to UTC and can be changed with SET TIME ZONE (equivalently SET timezone = ...). Supported zones are UTC/GMT and fixed offsets: a bare '+07' means seven hours east, a colon form such as '+05:30' follows the POSIX convention (five and a half hours west), and a number or INTERVAL value counts hours east. SET TIME ZONE LOCAL, SET TIME ZONE DEFAULT, and RESET timezone restore UTC. The zone shifts how timestamptz values render and how input without an explicit offset is read, along with CURRENT_TIME, CURRENT_DATE, LOCALTIMESTAMP, wall-clock casts, EXTRACT, date_trunc, and to_char. Region names such as 'Asia/Jakarta' are refused: they need a time-zone database (daylight-saving rules) that the engine does not carry. AT TIME ZONE accepts UTC and numeric offsets such as +07:00 under the same rule.

sql
SET TIME ZONE '+07';
SELECT TIMESTAMPTZ '2026-08-30 12:00:00+00';  -- 2026-08-30 19:00:00+07
SELECT TIMESTAMPTZ '2026-08-30 12:00:00';     -- read as +07 wall time
SHOW timezone;                                -- <+07>-07
RESET timezone;

JSON

JSON and JSONB both store a parsed value. See How JSON is stored.

sql
CREATE TABLE docs (id INT PRIMARY KEY, body JSONB);
INSERT INTO docs VALUES (1, '{"user":{"name":"ana","tags":["a","b"]},"active":true}');

SELECT body -> 'user' ->> 'name'                AS name,
       body #>> '{user,tags,0}'                 AS first_tag,
       body @> '{"active":true}'                AS is_active,
       jsonb_exists(body, 'active')             AS has_key,     -- the ? operator, as a function
       jsonb_path_query_first(body, '$.user.tags[*]') AS tag
FROM   docs;

-- Build and modify
SELECT jsonb_build_object('id', id, 'name', body -> 'user' ->> 'name') FROM docs;
UPDATE docs SET body = jsonb_set(body, '{user,name}', '"budi"') WHERE id = 1;

-- Expand: one row per element / per key (a set-returning function goes in the select list)
SELECT id, jsonb_array_elements_text(body #> '{user,tags}') AS tag FROM docs;
SELECT id, jsonb_object_keys(body) AS key FROM docs;

The ? operator is not available because ? is reserved for query parameters; use jsonb_exists(doc, key) instead.

Bit strings

BIT(n) and BIT VARYING(n), with literals B'1011' and X'0f'.

sql
SELECT B'1011' & B'1101'  AS and_,
       B'1011' | B'1101'  AS or_,
       ~B'1011'           AS not_,
       B'1011' << 1       AS shifted,
       length(B'1011')    AS len;

A bit string of either kind can be stored in a column of either kind. BIT(n) takes exactly n bits (22026 otherwise) and BIT VARYING(n) at most n (22001 otherwise); storing a value never pads or truncates it. An explicit cast does: B'10101'::bit(3) is 101, B'1'::bit(3) is 100. The two kinds compare with each other whatever their lengths.

sql
CREATE TABLE flags (v BIT VARYING(8), f BIT(3));
INSERT INTO flags (v) VALUES (B'101');       -- ok
INSERT INTO flags (f) VALUES (B'1010');      -- ERROR 22026
INSERT INTO flags (v) VALUES (B'101010101'); -- ERROR 22001

Vectors

VECTOR(n) with four distance operators and an HNSW index.

sql
CREATE TABLE items (id INT PRIMARY KEY, emb VECTOR(3));
INSERT INTO items VALUES (1, '[1,0,0]'), (2, '[0,1,0]');

CREATE INDEX items_emb ON items USING hnsw (emb vector_cosine_ops);

SET hnsw_ef_search = 100;                    -- higher trades latency for recall
SELECT id, emb <=> '[1,0,0]' AS distance
FROM   items ORDER BY distance LIMIT 5;

Operators: <-> L2, <=> cosine, <#> negative inner product, <+> L1. Operator classes: vector_l2_ops, vector_cosine_ops, vector_ip_ops, vector_l1_ops. An index answers only the metric its operator class declared, so build one index per metric you query; EXPLAIN says whether a query used the index or fell back to an exact scan.

Enumerated and composite types

sql
CREATE TYPE mood AS ENUM ('sad', 'ok', 'happy');
CREATE TYPE point3 AS (x INT, y INT, z INT);

CREATE TABLE t (id INT, m mood, p point3);
INSERT INTO t VALUES (1, 'happy', '(1,2,3)');
SELECT m, p FROM t;
--    m    |    p
-- --------+---------
--  happy  | (1,2,3)

DROP TABLE t;
DROP TYPE point3;

An enum value outside its label list is rejected on insert (22P02). Enum comparison and MIN / MAX follow the declaration order of the labels, not the label text, and mixing two different enum types in a comparison, CASE, COALESCE, GREATEST / LEAST or NULLIF is refused (42883 / 42846) rather than compared by position.

A composite value is written as ROW(...) or in its '(a,b,c)' text form, and a single field is read back with (value).field:

sql
CREATE TYPE pair AS (x INT, y TEXT);
CREATE TABLE cpx (id INT, p pair);
INSERT INTO cpx VALUES (1, ROW(7, 'seven')::pair), (2, '(8,eight)'::pair);

SELECT id, (p).x, (p).y FROM cpx ORDER BY id;
--  id | x | y
-- ----+---+-------
--   1 | 7 | seven
--   2 | 8 | eight

UPDATE cpx SET p = ROW(70, 'seventy')::pair WHERE (p).x = 7;
DELETE FROM cpx WHERE (p).x = 8;

(value).* expands a composite value into one column per field, named after the field. It is a SELECT-list item only and takes no alias. A positional ORDER BY n counts the expanded columns; a positional GROUP BY n counts the items as written, so it cannot name a (value).* item:

sql
SELECT id, (p).* FROM cpx ORDER BY id;
--  id | x | y
-- ----+---+-------
--   1 | 7 | seven

The fields of every composite type are listed in information_schema.attributes (udt_name, attribute_name, ordinal_position, data_type, and the length, precision and scale columns), and the types themselves in information_schema.user_defined_types. Types carry no privileges, so every role can read both.

A bare ROW(a, b) with no cast is an anonymous record: it renders in the canonical text form ((1,"a b")), compares field by field, and its fields are read as .f1 .. .fN:

sql
SELECT ROW(1, 'a b') AS r, (ROW(1, 'a')).f2 AS second;
--        r        | second
-- ---------------+-------
--  (1,"a b")     | a
SELECT (ROW(1, 'a')).f3;
-- ERROR 42703: could not identify column "f3" in record data type

A row value can be compared (ROW(a, b) = ROW(1, 'x')) and counted, but not aggregated by sum / min / max.

A field can be of another composite type. In the text form the nested value is quoted like any text, and field access chains through the levels:

sql
CREATE TYPE inner_t AS (x INT, t TEXT);
CREATE TYPE outer_t AS (y inner_t, z INT);
CREATE TABLE nested (v outer_t);
INSERT INTO nested VALUES (ROW(ROW(1, 'a b')::inner_t, 2)::outer_t), ('("(10,x)",3)');

SELECT v, (v).y.x FROM nested;
--          v          | x
-- --------------------+----
--  ("(1,""a b"")",2)  |  1
--  ("(10,x)",3)       | 10

Text input is checked against every level ('("(abc,x)",3)' is refused), a comparison orders a nested field by its own fields, and a type another composite type uses cannot be dropped (2BP01). A field can also be any built-in type whose text form needs quoting, such as BYTEA, INTERVAL or an array: '("\\x01","1 day","{1,2}")'::cx reads back as it was written. Arrays of a composite type are not supported yet.

ORDER BY a composite column sorts by its text form, not field by field.

Creating and changing objects

Tables

sql
CREATE TABLE customers (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email    TEXT NOT NULL UNIQUE,
  country  TEXT DEFAULT 'ID',
  spend    NUMERIC(12,2) CHECK (spend >= 0),
  tax      NUMERIC(12,2) GENERATED ALWAYS AS (spend * 0.11) STORED,
  joined   TIMESTAMPTZ DEFAULT now()
);

CREATE TABLE orders (
  id       BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer BIGINT REFERENCES customers (id) ON DELETE CASCADE,
  total    NUMERIC(12,2),
  placed   TIMESTAMPTZ DEFAULT now(),
  CONSTRAINT total_positive CHECK (total > 0)
);

CREATE TABLE IF NOT EXISTS archive (LIKE orders);   -- copy the shape, not the rows
CREATE TABLE archive2 (LIKE orders INCLUDING ALL);  -- also defaults, checks, keys, indexes
CREATE TABLE recent AS SELECT * FROM orders WHERE total > 100;
DROP TABLE IF EXISTS recent;

The bare LIKE copies columns with their types, widths and NOT NULL. The options add more: INCLUDING DEFAULTS (a SERIAL column's default keeps drawing from the source's sequence), INCLUDING CONSTRAINTS (user CHECKs), INCLUDING INDEXES (primary key, unique constraints and secondary indexes, renamed onto the new table), INCLUDING IDENTITY (with a fresh sequence), INCLUDING GENERATED, and INCLUDING ALL for everything. COMMENTS, STATISTICS, STORAGE and COMPRESSION are accepted with nothing to copy. Foreign keys are never copied.

CREATE UNLOGGED TABLE is accepted, and the table is stored like any other, with full crash durability, because the write-ahead log is the only durable copy of the data. Queries behave the same as on any table.

Constraints available: PRIMARY KEY, UNIQUE, NOT NULL, CHECK, FOREIGN KEY ... REFERENCES with ON DELETE / ON UPDATE CASCADE, SET NULL, SET DEFAULT, RESTRICT, NO ACTION; each can be written at column or table level. SET DEFAULT is accepted in a definition, but a delete or update that would run it is refused (0A000). A PRIMARY KEY makes its columns NOT NULL, also when it is declared as a table constraint or added with ALTER TABLE ... ADD; the ADD is refused (23502) while a row holds a NULL in one of them. Generated columns are STORED. With UNIQUE NULLS NOT DISTINCT, NULL keys count as equal:

sql
CREATE TABLE nnd (a INT, b TEXT, UNIQUE NULLS NOT DISTINCT (a));
INSERT INTO nnd (a) VALUES (NULL);
INSERT INTO nnd (a) VALUES (NULL);
-- ERROR 23505: with NULLS NOT DISTINCT, NULLs count as equal; plain UNIQUE allows both

UNIQUE NULLS NOT DISTINCT allows at most one row with a NULL key; plain UNIQUE allows any number. It also works through ALTER TABLE ... ADD. Exclusion constraints are described under Exclusion constraints.

ON DELETE SET NULL (column [, ...]) sets only the listed referencing columns to NULL when the referenced row is deleted. The other columns of the foreign key keep their values. The list is accepted at column level, at table level and in ALTER TABLE ... ADD CONSTRAINT.

sql
CREATE TABLE dept (org INT NOT NULL, d_id INT NOT NULL, name TEXT NOT NULL,
  PRIMARY KEY (d_id), UNIQUE (org, d_id, name));
CREATE TABLE vendor (v_id INT PRIMARY KEY, org INT NOT NULL, d_id INT, name TEXT,
  CONSTRAINT vendor_dept_fkey FOREIGN KEY (org, d_id, name)
    REFERENCES dept (org, d_id, name) ON DELETE SET NULL (d_id));
INSERT INTO dept VALUES (7, 1, 'ops'), (7, 2, 'sales');
INSERT INTO vendor VALUES (10, 7, 1, 'ops'), (11, 7, 2, 'sales');
DELETE FROM dept WHERE d_id = 1;
SELECT v_id, org, d_id, name FROM vendor ORDER BY v_id;
--  v_id | org | d_id | name
-- ------+-----+------+-------
--    10 |   7 | NULL | ops
--    11 |   7 |    2 | sales

Each listed column must be one of the foreign key's referencing columns (42P10). A column list on ON UPDATE, and SET DEFAULT (column, ...), are refused with 0A000. A listed NOT NULL column fails the delete with 23502. information_schema.referential_constraints.delete_rule reports SET NULL.

Rows that a foreign key action rewrites (ON DELETE SET NULL, ON UPDATE CASCADE) must satisfy the child table's CHECK constraints and unique keys. A violation fails the statement on the parent table with 23514 or 23505.

Temporary tables belong to the session that made them, are invisible to others, and disappear when the session ends. ON COMMIT DELETE ROWS and ON COMMIT DROP are accepted.

sql
CREATE TEMP TABLE scratch (id INT) ON COMMIT DROP;

Exclusion constraints

Syntax: [CONSTRAINT name] EXCLUDE [USING gist | btree] (element WITH operator [, ...]) [WHERE (predicate)]. An element is a column or an expression. The operator is = or && (range overlap, for int4range, int8range, numrange, daterange, tsrange and tstzrange). Two rows conflict when every operator holds between them. With WHERE, only the rows that satisfy the predicate are checked.

sql
CREATE TABLE booking (
  room      INT,
  during    INT4RANGE,
  cancelled BOOL NOT NULL DEFAULT false,
  CONSTRAINT booking_no_overlap
    EXCLUDE USING gist (room WITH =, during WITH &&) WHERE (NOT cancelled)
);
INSERT INTO booking (room, during) VALUES (1, '[1,5)');
INSERT INTO booking (room, during) VALUES (1, '[5,9)');   -- the ranges only touch
INSERT INTO booking (room, during) VALUES (2, '[3,6)');   -- another room
INSERT INTO booking (room, during) VALUES (1, '[3,6)');
-- ERROR 23P01: conflicting key value violates exclusion constraint "booking_no_overlap":
--   key (room, during)=(1, [3,6)) conflicts with existing key (room, during)=(1, [1,5))
INSERT INTO booking VALUES (1, '[3,6)', true);            -- cancelled: not checked

ALTER TABLE booking ADD CONSTRAINT booking_all EXCLUDE (room WITH =, during WITH &&);
-- ERROR 23P01: the existing rows (1, [1,5)) and (1, [3,6)) conflict

A row with a NULL element or an empty range never conflicts. Range bounds are respected, so [1,5) and [5,9) do not overlap. USING gist (the default) and USING btree behave the same. The constraint is checked by INSERT, UPDATE, MERGE, COPY and ON CONFLICT; ON CONFLICT DO NOTHING skips a conflicting row, and ON CONFLICT ... DO UPDATE needs a UNIQUE arbiter. ALTER TABLE ... ADD CONSTRAINT ... EXCLUDE checks the existing rows. Elements and the predicate may call only immutable functions (42P17). information_schema.table_constraints lists the constraint with constraint_type EXCLUDE. When every element is a plain column WITH = and there is no WHERE, the constraint is created as a UNIQUE constraint on those columns.

The check sees every committed row at any isolation level. Of two transactions that write rows with the same = values at the same time, the second fails at once with 40001, or with 23P01 if the first has already committed.

Errors: 23P01 for a conflict. 0A000 for another operator, another access method, INCLUDE, or an EXCLUDE on a partitioned table (declare it on each partition).

Deferrable constraints

Syntax: [NOT] DEFERRABLE [INITIALLY DEFERRED | INITIALLY IMMEDIATE] after a PRIMARY KEY, UNIQUE, FOREIGN KEY or EXCLUDE constraint, at column or table level. A deferred constraint is checked at COMMIT instead of by each statement. NOT DEFERRABLE is the default. DEFERRABLE alone starts each transaction in immediate mode; INITIALLY DEFERRED starts it in deferred mode.

sql
CREATE TABLE slot (
  n    INT CONSTRAINT slot_n UNIQUE DEFERRABLE INITIALLY DEFERRED,
  name TEXT
);
INSERT INTO slot VALUES (1, 'a'), (2, 'b');
BEGIN;
UPDATE slot SET n = 2 WHERE name = 'a';   -- two rows hold 2 for now
UPDATE slot SET n = 1 WHERE name = 'b';
COMMIT;                                   -- slot_n is checked here

BEGIN;
INSERT INTO slot VALUES (1, 'c');
COMMIT;
-- ERROR 23505: constraint violation: duplicate key violates unique constraint "slot_n" on (n)

CREATE TABLE version (
  id   INT PRIMARY KEY,
  prev INT REFERENCES version (id) DEFERRABLE INITIALLY DEFERRED
);
BEGIN;
INSERT INTO version VALUES (2, 1);        -- row 1 does not exist yet
INSERT INTO version VALUES (1, NULL);
COMMIT;

SET CONSTRAINTS {ALL | name [, ...]} {DEFERRED | IMMEDIATE} sets the mode until the transaction ends. IMMEDIATE also checks, at once, what the named constraints have deferred so far. A name may be schema-qualified. Outside a transaction block the statement only raises a warning. ALTER TABLE t ALTER CONSTRAINT name [NOT] DEFERRABLE [INITIALLY DEFERRED | INITIALLY IMMEDIATE] changes the declared mode.

sql
CREATE TABLE acct (id INT PRIMARY KEY, code INT CONSTRAINT acct_code UNIQUE DEFERRABLE);
INSERT INTO acct VALUES (1, 10), (2, 20);
BEGIN;
SET CONSTRAINTS acct_code DEFERRED;       -- or SET CONSTRAINTS ALL DEFERRED
UPDATE acct SET code = 20 WHERE id = 1;
UPDATE acct SET code = 10 WHERE id = 2;
SET CONSTRAINTS acct_code IMMEDIATE;      -- checks the pending rows now
COMMIT;

ALTER TABLE acct ALTER CONSTRAINT acct_code DEFERRABLE INITIALLY DEFERRED;
SELECT constraint_name, is_deferrable, initially_deferred
FROM   information_schema.table_constraints
WHERE  table_name = 'acct' ORDER BY constraint_name;
--  constraint_name | is_deferrable | initially_deferred
-- -----------------+---------------+--------------------
--  acct_code       | YES           | YES
--  acct_pkey       | NO            | NO

For a foreign key, only the NO ACTION check is deferred. RESTRICT is checked at once, and CASCADE and SET NULL run when the parent row changes. A deferrable constraint cannot be the arbiter of ON CONFLICT (0A000). CHECK and NOT NULL constraints cannot be deferred. How a failed check at COMMIT ends the transaction is described under deferred constraint checks.

Errors: a violation reports the constraint's own code (23505, 23503, 23P01). 42704 for an unknown name in SET CONSTRAINTS, 55000 for a constraint that is not deferrable, 42601 for NOT DEFERRABLE INITIALLY DEFERRED, 0A000 for DEFERRABLE on a CHECK, 42809 for ALTER CONSTRAINT on a CHECK.

Partitioned tables

A table can be split by ranges, by value lists, or by hash. The parent stores no rows: an insert into it is routed to the matching partition, a query on it reads the partitions the WHERE clause cannot rule out, and a row that fits no partition is refused.

sql
CREATE TABLE events (id INT, region INT) PARTITION BY RANGE (region);
CREATE TABLE events_lo PARTITION OF events FOR VALUES FROM (0)   TO (100);
CREATE TABLE events_hi PARTITION OF events FOR VALUES FROM (100) TO (200);

INSERT INTO events VALUES (1, 50), (2, 150);      -- routed to events_lo / events_hi
SELECT id, region FROM events ORDER BY id;        -- reads both partitions
SELECT id FROM events WHERE region = 42;          -- prunes: only events_lo is scanned

INSERT INTO events VALUES (3, 500);
-- ERROR 23514: no partition of relation "events" found for the inserted row
INSERT INTO events_lo VALUES (4, 150);
-- ERROR 23514: the inserted row does not belong to partition "events_lo"

The three strategies, plus a catch-all partition:

sql
CREATE TABLE traffic (id INT, region TEXT) PARTITION BY LIST (region);
CREATE TABLE traffic_asia PARTITION OF traffic FOR VALUES IN ('ID', 'SG', 'JP');
CREATE TABLE traffic_rest PARTITION OF traffic DEFAULT;
INSERT INTO traffic VALUES (1, 'ID'), (2, 'US'), (3, NULL);   -- 2 and 3 land in traffic_rest

CREATE TABLE loads (id INT, v TEXT) PARTITION BY HASH (id);
CREATE TABLE loads_0 PARTITION OF loads FOR VALUES WITH (MODULUS 3, REMAINDER 0);
CREATE TABLE loads_1 PARTITION OF loads FOR VALUES WITH (MODULUS 3, REMAINDER 1);
CREATE TABLE loads_2 PARTITION OF loads FOR VALUES WITH (MODULUS 3, REMAINDER 2);

A range key may span several columns, compared as a tuple, and a partition may itself be partitioned:

sql
CREATE TABLE metrics (y INT, mo INT, v TEXT) PARTITION BY RANGE (y, mo);
CREATE TABLE metrics_q2 PARTITION OF metrics FOR VALUES FROM (2026, 4) TO (2026, 7);

CREATE TABLE logs (y INT, mo INT) PARTITION BY RANGE (y);
CREATE TABLE logs_2026 PARTITION OF logs
  FOR VALUES FROM (2026) TO (2027) PARTITION BY RANGE (mo);
CREATE TABLE logs_2026_h1 PARTITION OF logs_2026 FOR VALUES FROM (1) TO (7);

An existing table with matching columns can be attached, and a partition detached into an ordinary table:

sql
CREATE TABLE events_archive (id INT, region INT);
ALTER TABLE events ATTACH PARTITION events_archive FOR VALUES FROM (200) TO (300);
ALTER TABLE events DETACH PARTITION events_archive;

Rules for partitioned tables:

  • Range bounds are constant literals, half-open [lo, hi), compared per tuple, so a multi-column key exactly on a boundary belongs to the upper partition. Overlap, lo >= hi, wrong bound arity, and a bound kind that does not match the parent's strategy are refused at creation, and ATTACH scans the table first and refuses if an existing row falls outside the bound.
  • The DEFAULT partition takes every row no sibling accepts, including a NULL key (a NULL key with no default partition is refused, since no range, list or hash bound matches NULL). A hash parent takes no default, and a new sibling whose bound overlaps rows already in the default is refused.
  • UPDATE and DELETE on the parent reach every partition; ONLY restricts them to the parent itself. An UPDATE through the parent that changes the partition key moves the row to the partition that accepts the new value. An UPDATE on a partition itself refuses to move the row out of its bound (23514).
  • Omitted columns take their defaults before a row is routed, so the partition key may come from a default. The planner prunes partitions using WHERE conditions of the shape key = / < / <= / > / >= constant and key BETWEEN a AND b, which shows in EXPLAIN as fewer scanned partitions.
  • DROP TABLE on the parent drops the whole partition tree with it.
  • Parent and partitions may live in different schemas; qualified names work everywhere.

A partition created with PARTITION OF takes the parent's column defaults, SERIAL and identity columns (drawing from the parent's sequence), generated columns, enum and domain types, and type limits such as VARCHAR(n). A row written straight into a partition gets the same values and checks as one written through the parent. ALTER TABLE parent ALTER COLUMN ... SET DEFAULT and DROP DEFAULT reach every partition. ATTACH PARTITION refuses a table whose column is generated where the parent's is not, or the reverse (42804).

sql
CREATE TABLE ledger (id SERIAL, region INT NOT NULL, status TEXT DEFAULT 'open')
  PARTITION BY LIST (region);
CREATE TABLE ledger_1 PARTITION OF ledger FOR VALUES IN (1);
INSERT INTO ledger (region) VALUES (1);
INSERT INTO ledger_1 (region) VALUES (1);
SELECT id, region, status FROM ledger ORDER BY id;
--  id | region | status
-- ----+--------+--------
--   1 |      1 | open
--   2 |      1 | open

Not accepted (0A000): LIST with more than one key column, non-literal bounds, a partition declaring its own columns, a FOREIGN KEY that references a partitioned table, a unique index or an EXCLUDE constraint on a partitioned table, and MERGE into a partitioned table. Use the partitions for these.

Keys on partitioned tables

A PRIMARY KEY or UNIQUE constraint on a partitioned table is copied to every partition, including one added later with PARTITION OF or ATTACH PARTITION. When the key includes every partition-key column, each partition enforces it on its own. A key that leaves out a partition-key column, or any key of a table partitioned by an expression, is enforced across all partitions. Creating such a key raises a notice, because every write of the key looks it up in every partition.

sql
CREATE TABLE audit_events (
  id         UUID PRIMARY KEY,
  created_at TIMESTAMP NOT NULL,
  payload    TEXT
) PARTITION BY RANGE (created_at);
-- NOTICE: unique constraint "audit_events_pkey" on partitioned table "audit_events" does not
--   include every partitioning column, so it is enforced across all of its partitions: every
--   write of its key probes every partition
CREATE TABLE audit_events_01 PARTITION OF audit_events FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');
CREATE TABLE audit_events_02 PARTITION OF audit_events FOR VALUES FROM ('2026-02-01') TO ('2026-03-01');

INSERT INTO audit_events VALUES ('6f1c8a52-0d0e-4d33-9a51-1f6b2a0c9e11', '2026-01-05', 'a');
INSERT INTO audit_events VALUES ('6f1c8a52-0d0e-4d33-9a51-1f6b2a0c9e11', '2026-02-05', 'b');
-- ERROR 23505: constraint violation: duplicate key violates primary key constraint
--   "audit_events_pkey" on (id)
INSERT INTO audit_events VALUES ('6f1c8a52-0d0e-4d33-9a51-1f6b2a0c9e11', '2026-02-05', 'b')
ON CONFLICT DO NOTHING;                   -- INSERT 0

Every write path is checked, including INSERT into a partition, COPY, an UPDATE that moves a row, and foreign key actions. ON CONFLICT DO NOTHING skips a row whose key another partition holds, and ON CONFLICT (key) DO UPDATE updates the row in the partition that holds it. Of two transactions that write the same key into any partitions at the same time, the second fails at once with 40001. ALTER TABLE ... ADD and ATTACH PARTITION check the existing rows of all partitions.

Refused with 0A000: such a key over a FLOAT, REAL, NUMERIC, INTERVAL, array, range, geometry, VECTOR, INET, CIDR, bit string, TSVECTOR, TSQUERY or XML column, and NULLS NOT DISTINCT on such a key.

Inherited tables

INHERITS gives a table its parents' columns in front of its own, and a query on the parent also reads every descendant. ONLY reads just the named table.

sql
CREATE TABLE cities   (name TEXT, pop INT);
CREATE TABLE capitals (state TEXT) INHERITS (cities);   -- columns: name, pop, state

INSERT INTO cities   VALUES ('Bandung', 2500000);
INSERT INTO capitals VALUES ('Jakarta', 10000000, 'JK');

SELECT name FROM cities ORDER BY name;        -- Bandung, Jakarta
SELECT name FROM ONLY cities;                 -- Bandung

UPDATE cities SET pop = pop + 1;              -- reaches capitals too
UPDATE ONLY cities SET pop = 0;               -- just the parent's own rows
DELETE FROM cities WHERE pop = 0;             -- likewise propagates; ONLY restricts

A child may redeclare an inherited column only with the same type; NOT NULL holds only if every copy has it. Dropping a parent that still has children is refused (2BP01); DROP TABLE ... CASCADE drops the descendants with it. Row-level security applies per table, so each descendant's policies govern its own rows.

Altering

One action per ALTER TABLE statement.

sql
ALTER TABLE orders ADD COLUMN note TEXT;
ALTER TABLE orders ADD COLUMN channel TEXT DEFAULT 'web' NOT NULL;
ALTER TABLE orders ADD COLUMN gross NUMERIC(12,2) GENERATED ALWAYS AS (total * 1.11) STORED;
ALTER TABLE orders ALTER COLUMN note SET DEFAULT '';
ALTER TABLE orders ALTER COLUMN note DROP DEFAULT;
ALTER TABLE orders ALTER COLUMN note SET NOT NULL;
ALTER TABLE orders ALTER COLUMN note DROP NOT NULL;
ALTER TABLE orders ALTER COLUMN note TYPE VARCHAR(200);
ALTER TABLE orders RENAME COLUMN note TO memo;
ALTER TABLE orders DROP COLUMN memo CASCADE;         -- also drops views, policies and triggers that read it
ALTER TABLE orders DROP COLUMN channel RESTRICT;      -- RESTRICT is the default
ALTER TABLE orders RENAME TO sales_orders;
ALTER TABLE sales_orders RENAME TO orders;

ALTER TABLE orders DROP CONSTRAINT total_positive;
ALTER TABLE orders ADD CONSTRAINT total_positive CHECK (total > 0);
ALTER TABLE orders ADD CONSTRAINT orders_customer_fk FOREIGN KEY (customer) REFERENCES customers (id);
ALTER TABLE orders ALTER CONSTRAINT orders_customer_fk DEFERRABLE INITIALLY DEFERRED;
ALTER TABLE orders DROP CONSTRAINT orders_customer_fk;
ALTER TABLE orders DROP CONSTRAINT IF EXISTS orders_customer_fk;

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE orders DISABLE ROW LEVEL SECURITY;

ALTER TABLE t DISABLE TRIGGER name and ENABLE TRIGGER name are shown under Triggers.

DROP COLUMN also drops what the table itself defines over the column, whether the column is its only one or one of several: indexes (including expression and partial indexes that read it), PRIMARY KEY, UNIQUE and CHECK constraints, foreign keys whose own columns include it, a USING hnsw vector index on it, its column-level grants, and generated columns computed from it. A SERIAL or identity column's sequence goes with it. Without CASCADE (or with RESTRICT), the drop is refused with 2BP01 while something outside the table still needs the column: a foreign key on another table (or a self-referencing one) that references it, or a view, materialized view, row-level-security policy or trigger (on this table or any other) whose SQL reads it. A view that reads the table through *, t.* or a NATURAL join counts as reading every column of it. With CASCADE those are dropped too; the referencing table itself and its rows stay. A function or procedure whose body reads the column refuses the drop even with CASCADE: replace or drop it first. Dropping the last column of a table, counting the generated columns that would go with it, is refused (42P16).

ALTER COLUMN ... DROP DEFAULT on a SERIAL or identity column also drops the sequence it drew from, unless another column's default still uses it. Dropping a sequence (directly or with its column or table) is transactional: until the dropping transaction ends, another transaction creating a sequence of the same name is refused with 40001, since a rollback would bring the dropped one back.

ALTER COLUMN ... TYPE replaces the range or length the old type enforced with the new type's: widening SMALLINT to INTEGER or BIGINT, or VARCHAR(10) to VARCHAR(50) or TEXT, lifts the old bound. Narrowing checks the rows already there, and a value the new type cannot hold refuses the change (22003 for an integer out of range, 22001 for a string that is too long).

RENAME COLUMN carries everything the table records under the column's name to the new name: its DEFAULT (including a SERIAL or identity sentinel; the backing sequence keeps its name), its type-range check, its indexes (plain, multi-column, expression and partial), PRIMARY KEY, UNIQUE and CHECK constraints, foreign keys on either side, generated expressions that read it, column-level grants, and its enum or composite type. A view, materialized view, policy, trigger, function or procedure keeps its SQL as text, which the rename does not rewrite: while one of them names the column, the rename is refused (2BP01) and the error names it. Drop that object, rename, and recreate it.

ADD COLUMN ... GENERATED ALWAYS AS (expr) STORED computes the column for every existing row as part of the statement, and every later insert or update recomputes it; an explicit value for it is refused (428C9). On a partitioned or inherited table the column is added to every partition and child the same way. The expression follows the same rules as in CREATE TABLE: it reads only the table's ordinary columns and calls only immutable functions (see Volatility).

Every column change is transactional: a ROLLBACK (or a ROLLBACK TO SAVEPOINT) restores the column, its data and everything the change dropped or moved, sequences included. DROP CONSTRAINT of a constraint the table does not have is an error (42704); with IF EXISTS it does nothing.

A statement that validates or rewrites a table's rows (ADD CHECK, SET NOT NULL, ADD UNIQUE, ADD FOREIGN KEY, ATTACH PARTITION, ADD COLUMN ... DEFAULT, a type change, an index build) takes the table exclusively and reads its latest committed rows. Next to a transaction that has written the table and has not yet ended, it fails with 40001 rather than waiting (next to a prepared transaction, 55006); see transactions.

Not accepted: ADD COLUMN ... FIRST | AFTER, ADD COLUMN ... PRIMARY KEY (add the column, then ADD CONSTRAINT ... PRIMARY KEY), ADD COLUMN with SERIAL or GENERATED AS IDENTITY (0A000), dropping several columns in one statement, ADD CONSTRAINT ... NOT VALID, ALTER COLUMN ... TYPE ... USING <expr>, ALTER COLUMN ... ADD GENERATED AS IDENTITY, and a comma-separated list of actions.

Indexes

sql
CREATE INDEX orders_customer ON orders (customer);
CREATE INDEX orders_big      ON orders (customer) WHERE total > 1000;   -- partial
CREATE INDEX orders_lower    ON customers ((lower(email)));             -- expression
CREATE UNIQUE INDEX customers_email ON customers (email);   -- an index needs a name
CREATE INDEX orders_desc     ON orders (total DESC);
CREATE INDEX IF NOT EXISTS orders_total ON orders (total) INCLUDE (customer);
CREATE INDEX orders_btree ON orders USING btree (customer);      -- btree is the default anyway
CREATE INDEX orders_nulls ON orders (total DESC NULLS FIRST);
DROP INDEX IF EXISTS orders_desc;

Index methods: the scalar structure is always the B-tree. USING btree names it explicitly; USING hash and USING brin record the declared method with the same tree answering the scans (it covers at least what those methods promise); USING gin, gist and spgist back onto the default tree; USING hnsw selects the vector index. An unknown method is an error (42704). A per-key NULLS FIRST / NULLS LAST is accepted; it does not change results, because a query whose ordering column is nullable is served by an explicit sort that follows the query's own NULLS clause. The planner picks an index from collected statistics, so run ANALYZE after a large load (see Maintenance).

A key expression or partial-index predicate that calls a function which is not immutable, such as now(), random() or uuidv7(), is refused when the index is created (42P17, see Volatility). An expression involving a TIMESTAMPTZ or TIMETZ value is accepted but never used to answer a query, because the session's TimeZone setting changes its value (CAST(ts AS DATE), extract(hour FROM ts)), so the key stored when a row was written need not be the value a later query computes. Index such a value through a stored generated column instead.

Unique indexes and NULL keys

Syntax: CREATE UNIQUE INDEX name ON table (columns) [NULLS [NOT] DISTINCT] [WHERE predicate]. With NULLS DISTINCT (the default), any number of rows may hold a NULL in a key column. With NULLS NOT DISTINCT, NULL counts as a value, so two NULL keys collide. With WHERE, only the rows that satisfy the predicate are checked.

sql
CREATE TABLE subscriptions (id UUID PRIMARY KEY, account TEXT, state TEXT NOT NULL);
CREATE UNIQUE INDEX subscriptions_one_active ON subscriptions (account)
  NULLS NOT DISTINCT WHERE state = 'active';
INSERT INTO subscriptions VALUES (gen_random_uuid(), NULL, 'active');
INSERT INTO subscriptions VALUES (gen_random_uuid(), NULL, 'ended');    -- not active
INSERT INTO subscriptions VALUES (gen_random_uuid(), NULL, 'active');
-- ERROR 23505: constraint violation: duplicate key violates unique index subscriptions_one_active

INSERT INTO subscriptions VALUES (gen_random_uuid(), NULL, 'active')
ON CONFLICT (account) WHERE state = 'active' DO UPDATE SET state = 'replaced';
SELECT account, state FROM subscriptions ORDER BY state;
--  account | state
-- ---------+----------
--  NULL    | ended
--  NULL    | replaced

ON CONFLICT (columns) uses a unique index over exactly those columns when no PRIMARY KEY or UNIQUE constraint matches. A partial unique index is used only with ON CONFLICT (columns) WHERE predicate, when each AND-ed condition of the index predicate also appears in that predicate; otherwise the statement fails with 42P10. A bare ON CONFLICT DO NOTHING skips a row that collides on any unique index. The index is checked by every write, including COPY, MERGE and foreign key actions.

A unique index created by an earlier release allowed only one NULL key. It now follows NULLS DISTINCT; see upgrades.

Errors: 23505 for a duplicate, also when CREATE UNIQUE INDEX finds one in the existing rows. 42601 for NULLS [NOT] DISTINCT on an index that is not UNIQUE. 0A000 for a unique index on a partitioned table; declare a UNIQUE constraint on it instead (see Keys on partitioned tables), or create the index on each partition.

Views, sequences, domains, schemas, databases

sql
CREATE VIEW big_orders AS SELECT * FROM orders WHERE total > 1000;
CREATE OR REPLACE VIEW big_orders AS SELECT * FROM orders WHERE total > 500;
DROP VIEW big_orders;

CREATE MATERIALIZED VIEW daily AS
  SELECT date_trunc('day', placed) AS d, count(*) AS n FROM orders GROUP BY 1;
REFRESH MATERIALIZED VIEW daily;

CREATE SEQUENCE invoice_no START 1000 INCREMENT BY 5;
SELECT nextval('invoice_no'), currval('invoice_no');
SELECT setval('invoice_no', 5000);
ALTER SEQUENCE invoice_no INCREMENT BY 10 MAXVALUE 100000;
ALTER SEQUENCE invoice_no RESTART WITH 2000;    -- the next nextval is exactly 2000
ALTER SEQUENCE invoice_no RESTART;              -- back to its START
DROP SEQUENCE invoice_no;

CREATE DOMAIN positive_int AS INT CHECK (VALUE > 0);
DROP DOMAIN positive_int;

CREATE SCHEMA reporting;
CREATE TABLE reporting.facts (id INT);
DROP SCHEMA reporting CASCADE;          -- RESTRICT (the default) refuses a non-empty schema

CREATE DATABASE app;                    -- a separate physical database; connect to it by name
DROP DATABASE app;

DROP SCHEMA without CASCADE, or with RESTRICT, refuses a schema that still holds a table, view or sequence (2BP01), and the message counts what it holds. DROP SCHEMA ... CASCADE drops each object in the schema the way its own DROP ... CASCADE would:

  • every table, with its indexes, constraints, column defaults, triggers, policies, comments, ownership and grants, and the sequences of its SERIAL and identity columns;
  • foreign keys that cross the schema boundary, in either direction: a table outside the schema that references a dropped table keeps its rows and loses only that foreign key;
  • the partitions of a partitioned table in the schema, wherever they live, and a partition in the schema whose parent lives elsewhere (the parent stays, without that partition);
  • the views and standalone sequences created in the schema. A view or sequence in the default schema whose name contains a dot (CREATE VIEW public."z.v") is not a member of schema z.
sql
CREATE SCHEMA reporting;
CREATE TABLE reporting.facts (id INT PRIMARY KEY);
CREATE VIEW reporting.recent AS SELECT id FROM reporting.facts;
CREATE TABLE notes (id INT, fact INT REFERENCES reporting.facts (id));

DROP SCHEMA reporting;
-- ERROR 2BP01: cannot drop schema "reporting": it holds 1 table(s),
-- 1 view(s) (drop them first or use DROP SCHEMA ... CASCADE)

DROP SCHEMA reporting CASCADE;
-- drops facts and recent, and removes the foreign key on notes

A view or materialized view outside the schema that reads a dropped table is not dropped, the same as with DROP TABLE: reading it fails with "table not found" until it is dropped or redefined.

The statement is one transaction step, so inside BEGIN a ROLLBACK restores the schema and everything in it. Dropping a foreign key takes the referenced table's lock without waiting: while another transaction is writing to a table outside the schema that a member table references, the drop fails with 40001; retry it once that transaction ends. A table another session commits into the schema while the drop runs is dropped with the rest; one it has created and not yet committed makes the drop fail with 40001.

A data directory written by an earlier release may still hold foreign keys, constraints and indexes of tables dropped by DROP SCHEMA ... CASCADE. The server removes them when it opens the database and logs each removed foreign key at WARN; until then, a foreign key whose other table no longer exists is skipped with a WARN log line. Views and sequences that such a release left under a dropped schema are not removed automatically, because that release did not record which schema a dotted name belongs to. Each is logged at open with the DROP VIEW or DROP SEQUENCE statement that removes it. For the same reason, a view or sequence that release created in a schema that still exists is not dropped by CASCADE nor counted by RESTRICT; drop it by name.

A view over a single table with no aggregate is auto-updatable: INSERT, UPDATE and DELETE through it reach the base table. With WITH CHECK OPTION, a row written through the view must stay visible through it:

sql
CREATE VIEW small_orders AS
  SELECT * FROM orders WHERE total < 100 WITH CHECK OPTION;
INSERT INTO small_orders (customer, total) VALUES (1, 500);
-- ERROR 44000: new row violates check option for view `small_orders`

The check applies to INSERT and UPDATE (a DELETE cannot make a row invisible-but-present). LOCAL and CASCADED are both accepted and behave the same, since an updatable view sits on one base table.

A materialized view holds the result of its last REFRESH. Incremental maintenance is opt-in with CREATE MATERIALIZED VIEW ... WITH (incremental = true) AS ...; a body that cannot be maintained incrementally is refused.

ALTER SEQUENCE takes any mix of INCREMENT [BY], MINVALUE / NO MINVALUE, MAXVALUE / NO MAXVALUE, START [WITH], RESTART [[WITH] n], CACHE n (accepted, no effect) and CYCLE / NO CYCLE, validates the merged definition, and IF EXISTS makes a missing sequence a no-op. information_schema.sequences lists every sequence with its bounds (a sequence created on an older release appears there after its first ALTER SEQUENCE). Sequence functions take the sequence name as a text literal and may only appear where they are evaluated exactly once: a SELECT without FROM, a VALUES row, or a column default.

CREATE DOMAIN accepts a base type and a CHECK; a DEFAULT or COLLATE on a domain is not accepted yet. A domain's CHECK follows the same volatility rule as a table's.

Comments

Syntax: COMMENT ON {TABLE | COLUMN | CONSTRAINT ... ON table | INDEX | TRIGGER ... ON table | FUNCTION | PROCEDURE | VIEW | MATERIALIZED VIEW | SCHEMA | SEQUENCE | TYPE | DOMAIN} name IS {'text' | NULL}. IS NULL or IS '' removes the comment; a new comment replaces the old one.

sql
COMMENT ON TABLE orders IS 'One row per checkout';
COMMENT ON COLUMN orders.total IS 'Gross, including tax';
COMMENT ON CONSTRAINT total_positive ON orders IS 'No zero or negative totals';
COMMENT ON INDEX orders_customer IS 'Serves the customer page';
COMMENT ON TRIGGER stock_changes ON stock IS 'Logs quantity changes';
COMMENT ON FUNCTION with_tax(numeric) IS 'Adds 11% tax';
COMMENT ON PROCEDURE countdown IS 'Counts down to zero';
COMMENT ON VIEW big_orders IS 'Orders over 1000';
COMMENT ON MATERIALIZED VIEW daily IS 'Refreshed hourly';
COMMENT ON SCHEMA reporting IS 'Report tables';
COMMENT ON SEQUENCE invoice_no IS 'Invoice numbers';
COMMENT ON TYPE mood IS 'How a reviewer felt';
COMMENT ON DOMAIN positive_int IS 'Integers above zero';
COMMENT ON TABLE orders IS NULL;        -- remove

SELECT object_type, object_name, description
FROM   information_schema.nusadb_comments
WHERE  table_name = 'orders' ORDER BY object_type;
--  object_type | object_name     | description
-- -------------+-----------------+----------------------------
--  COLUMN      | total           | Gross, including tax
--  CONSTRAINT  | total_positive  | No zero or negative totals
--  INDEX       | orders_customer | Serves the customer page

A table, and the table of a column, constraint or trigger, is found through the search_path or an explicit schema. A view or sequence is found in the current schema unless qualified, and functions, procedures, materialized views, types and domains in public. A function or procedure may be named without its argument list; when the list is given, only its length is compared with the routine's parameters.

Commenting on an object needs its owner or a superuser. Views, sequences, functions, procedures, types and domains can be commented on only by a superuser. Comments are transactional and durable. Renaming an object keeps its comment, and dropping it, directly or by cascade, removes the comment.

information_schema.nusadb_comments has one row per comment, with the columns object_type, object_schema, table_name (the table a column, constraint, index or trigger belongs to, the table itself for a table comment, otherwise NULL), object_name and description. A comment that belongs to a table is listed only to its owner, a role with a privilege on the table, or a superuser.

Errors: 42P01 for an unknown table or view, 42703 for an unknown column, 42704 for an unknown constraint, index, trigger, sequence, type or domain, 42883 for an unknown function or procedure, 3F000 for an unknown schema, 42501 without the required ownership.

Inserting and changing rows

sql
INSERT INTO customers (email, country) VALUES ('ana@example.com', 'ID')
RETURNING id, joined;

INSERT INTO archive SELECT * FROM orders WHERE total < 10;

INSERT INTO customers (email) VALUES ('ana@example.com')
ON CONFLICT DO NOTHING;

INSERT INTO customers (email, country) VALUES ('ana@example.com', 'SG')
ON CONFLICT (email) DO UPDATE SET country = EXCLUDED.country
WHERE customers.country <> EXCLUDED.country;

INSERT INTO tickets (id, note) OVERRIDING SYSTEM VALUE VALUES (99, 'imported');
-- without OVERRIDING SYSTEM VALUE, writing to a GENERATED ALWAYS identity column is ERROR 428C9.
-- OVERRIDING USER VALUE is the reverse: on a GENERATED BY DEFAULT column it ignores the supplied
-- value and takes the sequence's instead.

UPDATE customers SET country = DEFAULT WHERE country = '';   -- back to 'ID'

UPDATE orders o SET total = total * 1.1
FROM   customers c
WHERE  o.customer = c.id AND c.country = 'ID'
RETURNING id, total;

DELETE FROM orders USING customers c
WHERE  orders.customer = c.id AND c.country = 'XX';

CREATE TABLE stock    (sku TEXT PRIMARY KEY, qty INT);
CREATE TABLE shipment (sku TEXT, qty INT);
INSERT INTO stock    VALUES ('A', 1), ('B', 5), ('C', 2);
INSERT INTO shipment VALUES ('A', 3), ('B', 0), ('D', 7);

MERGE INTO stock t USING shipment s ON t.sku = s.sku
WHEN MATCHED AND s.qty = 0   THEN DELETE
WHEN MATCHED                 THEN UPDATE SET qty = t.qty + s.qty
WHEN NOT MATCHED             THEN INSERT (sku, qty) VALUES (s.sku, s.qty)
WHEN NOT MATCHED BY SOURCE   THEN UPDATE SET qty = 0;

SELECT * FROM stock ORDER BY sku;
--  sku | qty
-- -----+-----
--  A   |   4
--  C   |   0
--  D   |   7

TRUNCATE shipment;
TRUNCATE stock RESTART IDENTITY;
TRUNCATE customers CASCADE;      -- also empties tables that reference it
DROP TABLE shipment;
DROP TABLE stock;

SET column = DEFAULT in an UPDATE or a MERGE ... THEN UPDATE assigns the column's default: its expression, the next value of its sequence, or NULL when it has none. It is not accepted in ON CONFLICT DO UPDATE (0A000). MERGE into a partitioned table is refused (0A000); merge into its partitions.

UPDATE ... FROM, DELETE ... USING and MERGE ... USING take a single named table as the extra source. A source with the same name as the target needs an alias on one side: UPDATE t ... FROM t and DELETE FROM t USING t fail with 42712, the rule a repeated name in a SELECT's FROM already follows.

NOT NULL is checked once per written row, after BEFORE triggers, on every path: INSERT ... VALUES and INSERT ... SELECT, COPY, both arms of MERGE and of ON CONFLICT DO UPDATE, UPDATE, partition routing and foreign key SET NULL actions. A BEFORE trigger can therefore replace a NULL before it is checked. A violation is 23502.

Bulk load and export

COPY streams rows in one exchange instead of a round trip per row. The only targets are STDIN and STDOUT; in the shell the data travels on the command's own standard streams.

shell
nusadb-cli -c "COPY customers FROM STDIN" < rows.tsv
nusadb-cli -c "COPY customers (email, country) FROM STDIN WITH (FORMAT csv, HEADER)" < rows.csv
nusadb-cli -c "COPY customers FROM STDIN WITH (DELIMITER '|', NULL '')" < rows.psv
nusadb-cli -c "COPY customers TO STDOUT" > out.tsv
nusadb-cli -c "COPY customers (email, country) TO STDOUT WITH (FORMAT csv, HEADER)" > out.csv
nusadb-cli -c "COPY (SELECT email FROM customers WHERE country = 'ID' ORDER BY email) TO STDOUT WITH (FORMAT csv)" > id.csv
nusadb-cli -c "COPY customers TO STDOUT (FORMAT binary)" > customers.bin
nusadb-cli -c "COPY customers FROM STDIN (FORMAT binary)" < customers.bin

Options: FORMAT text | csv | binary, DELIMITER 'c', NULL 'string', HEADER, and for CSV only QUOTE 'c' and ESCAPE 'c'. The text format is tab-delimited with \N for NULL. The binary format (also spelled ... FROM STDIN BINARY) sends each value in its binary wire layout, framed by length, and takes none of the other options; its stream layout is in the wire protocol reference. Export takes a table (optionally with a column list) or a (query); the query form is TO STDOUT only, runs with the caller's privileges and row policies like any SELECT, and resolves unqualified names in the default schema, so qualify names from other schemas. Load takes a table only. A load larger than --copy-max-bytes is refused rather than buffered without bound. Columns a load leaves out take their defaults, also on a partitioned table.

Common table expressions

A recursive walk over a graph that may loop uses CYCLE to stop instead of running forever:

sql
CREATE TABLE edge (src INT, dst INT);
INSERT INTO edge VALUES (1,2), (2,3), (3,1);

WITH RECURSIVE walk(id, depth) AS (
  SELECT 1, 0
  UNION ALL
  SELECT e.dst, walk.depth + 1 FROM walk JOIN edge e ON walk.id = e.src
) CYCLE id SET is_cycle USING path
SELECT id, depth, is_cycle FROM walk ORDER BY depth;
--  id | depth | is_cycle
-- ----+-------+---------
--   1 |     0 | false
--   2 |     1 | false
--   3 |     2 | false
--   1 |     3 | true

The CTE needs an explicit column list; CYCLE col SET mark USING path appends two more columns to it: mark (true on the row that revisits a value) and path (the array of visited values), and recursion stops descending past a marked row. One cycle column only, and the boolean marker form only.

Full-text search

Text is turned into a tsvector (a sorted list of lexemes with positions) and matched against a tsquery with @@. Three configurations exist: simple lower-cases words; english (the default) also removes stop words and stems; and indonesian removes Indonesian stop words and applies a dictionary-free, rule-based Indonesian stemmer, so inflected forms of one root match each other (membaca, dibaca, bacaan all reduce to baca). Without a dictionary, the stemmer cannot always recover a root formed by consonant elision (memakan) or a word that only looks affixed (sekolah). It reduces such words the same way every time, so documents and queries still match.

sql
CREATE TABLE articles (id INT PRIMARY KEY, body TEXT);
INSERT INTO articles VALUES
  (1, 'The quick brown fox jumps over the lazy dog'),
  (2, 'A slow red fox');

SELECT to_tsvector('simple', 'The quick brown fox');
-- 'brown':3 'fox':4 'quick':2 'the':1

SELECT to_tsvector('english', 'The quick brown foxes');
-- 'brown':3 'fox':4 'quick':2

SELECT id FROM articles
WHERE  to_tsvector('english', body) @@ to_tsquery('english', 'quick & fox');
--  id
-- ----
--   1

SELECT id, ts_rank(to_tsvector(body), plainto_tsquery('red fox')) AS score
FROM   articles
WHERE  to_tsvector(body) @@ plainto_tsquery('red fox')
ORDER  BY score DESC;

Query operators: & and, | or, ! not, <-> / <N> phrase (followed-by at exactly N positions), with parentheses. to_tsquery takes that syntax; plainto_tsquery takes plain words and ANDs them; phraseto_tsquery takes plain words and chains them into a phrase whose distances mirror the word positions (phraseto_tsquery('the cat and the rat') is 'cat' <3> 'rat'). tsquery_phrase(a, b [, distance]) and a <-> b join two queries into a phrase. Phrase matching is position-accurate: to_tsvector('a b c') @@ 'a <2> c' holds, 'a <-> c' does not, and a strip()-ed vector never matches a phrase. Ranking: ts_rank, ts_rank_cd; setweight(vector, 'A') marks lexemes, strip(vector) drops positions. Other configurations and prefix matching are refused with an error. For hybrid search over a vector index and a text match, rrf_score(rank [, k]) fuses two rankings.

Routines and triggers

Functions

A function is LANGUAGE SQL (the default) or NusaScript (LANGUAGE nusascript). A SQL body is a single SELECT <expression> without FROM, inlined at each call site. A NusaScript body is a BEGIN ... END block whose RETURN <expr> produces the value, coerced to the declared RETURNS type; it may run several statements, branch, loop, and recurse. Parameters are available by name and as $1..$n.

sql
CREATE FUNCTION with_tax(amount NUMERIC) RETURNS NUMERIC
LANGUAGE SQL AS 'SELECT $1 * 1.11';

CREATE OR REPLACE FUNCTION greet(name TEXT) RETURNS TEXT AS $$ SELECT 'hello, ' || $1 $$;

CREATE FUNCTION fact(n INT) RETURNS INT LANGUAGE nusascript AS $$
BEGIN
  IF n <= 1 THEN
    RETURN 1;
  END IF;
  RETURN n * fact(n - 1);
END
$$;

SELECT with_tax(100), greet('ana'), fact(5);
--  with_tax | greet      | fact
-- ----------+------------+------
--    111.00 | hello, ana |  120

DROP FUNCTION greet;          -- by name, without a parameter list

A NusaScript function whose body ends without reaching a RETURN <value> fails with 2F005, and runaway recursion is stopped at a nesting limit rather than overflowing the stack.

Procedures and CALL

A procedure body is a $$ ... $$ block of statements. A plain sequence of SQL statements is fine; a body that starts with BEGIN is a NusaScript block with variables and control flow. Parameters are $1..$n. CALL runs the procedure inside the caller's transaction. nusadb-cli keeps $$ ... $$ bodies intact when splitting a batch, so these work from the shell and from any driver.

sql
CREATE TABLE audit (what TEXT, n INT);

CREATE PROCEDURE classify(v INT) AS $$
BEGIN
  DECLARE label TEXT;
  IF $1 > 100 THEN
    SET label = 'big';
  ELSIF $1 > 10 THEN
    SET label = 'medium';
  ELSE
    SET label = 'small';
  END IF;
  INSERT INTO audit VALUES (label, $1);
END
$$;

CREATE PROCEDURE countdown(start INT) AS $$
BEGIN
  DECLARE i INT DEFAULT $1;
  WHILE i > 0 LOOP
    INSERT INTO audit VALUES ('tick', i);
    SET i = i - 1;
  END LOOP;
END
$$;

CREATE PROCEDURE guarded(v INT) AS $$
BEGIN
  IF $1 < 0 THEN
    RAISE 'negative input';
  END IF;
  INSERT INTO audit VALUES ('ok', $1);
EXCEPTION WHEN OTHERS THEN
  INSERT INTO audit VALUES ('failed', $1);
END
$$;

CALL classify(500);
CALL countdown(3);
CALL guarded(-1);
SELECT * FROM audit ORDER BY what, n;
--   what  |  n
-- --------+-----
--  big    | 500
--  failed |  -1
--  tick   |   1
--  tick   |   2
--  tick   |   3

DROP PROCEDURE countdown;

CALL loud(-1) on a body without a handler reports P0001: raised exception: negative input and the caller's statement fails.

NusaScript statements: DECLARE name TYPE [DEFAULT expr], SET name = expr, IF ... THEN ... [ELSIF ...] [ELSE ...] END IF, WHILE cond LOOP ... END LOOP, FOR i IN low TO high LOOP ... END LOOP, RAISE 'message' (reported as P0001), RETURN, PERFORM expr (evaluate and discard, for a call made for its side effects), and any SQL data statement. An EXCEPTION WHEN OTHERS THEN handler rolls the body's writes back to a savepoint and runs in their place. Variables may be referenced by name inside embedded SQL; a column of the same name wins.

RAISE level 'format' [, value ...] fills each % in the format with the next value (%% is a literal %, NULL shows as <NULL>, and the counts must match, 42601 otherwise). EXCEPTION aborts like RAISE 'message'; NOTICE, INFO and WARNING send the message to the client as a notice and carry on; LOG and DEBUG carry on and send nothing.

sql
DO $$
BEGIN
  RAISE NOTICE 'archived % rows into %', 12, 'audit_2026';
  RAISE WARNING 'quota at %%: %', 95;    -- WARNING: quota at %: 95
END
$$;

Notices reach a client that negotiated protocol 1.3 (see notices). At most 1000 are kept per statement; the rest are dropped and counted by one closing WARNING. Besides RAISE, the server sends one for every IF EXISTS that found nothing to drop (NOTICE: table "t" does not exist, skipping) and every IF NOT EXISTS that found the object already there (NOTICE: relation "t" already exists, skipping, code 42P07).

DO blocks

The same body grammar, run once without parameters:

sql
DO $$
BEGIN
  DECLARE n INT DEFAULT 3;
  WHILE n > 0 LOOP
    INSERT INTO audit VALUES ('do', n);
    SET n = n - 1;
  END LOOP;
END
$$;

Triggers

A trigger runs one SQL statement when a table is written. NEW.col and OLD.col refer to the affected row.

sql
CREATE TABLE stock (sku TEXT PRIMARY KEY, qty INT);
CREATE TABLE stock_log (sku TEXT, before INT, after INT, at TIMESTAMPTZ DEFAULT now());

CREATE TRIGGER stock_changes
AFTER UPDATE ON stock
FOR EACH ROW
WHEN (NEW.qty <> OLD.qty)
INSERT INTO stock_log (sku, before, after) VALUES (OLD.sku, OLD.qty, NEW.qty);

INSERT INTO stock VALUES ('A-77', 10);
UPDATE stock SET qty = 8 WHERE sku = 'A-77';
SELECT sku, before, after FROM stock_log;
--  sku  | before | after
-- ------+--------+-------
--  A-77 |     10 |     8

ALTER TABLE stock DISABLE TRIGGER stock_changes;
ALTER TRIGGER stock_changes ON stock RENAME TO log_stock;
DROP TRIGGER log_stock ON stock;

Syntax: CREATE [OR REPLACE] TRIGGER name {BEFORE | AFTER} {INSERT | UPDATE | DELETE} [OR ...] ON table FOR EACH {ROW | STATEMENT} [WHEN (condition)] <action>. The action is one INSERT, UPDATE, DELETE or SELECT statement, or EXECUTE FUNCTION name() naming a NusaScript function, so several triggers can share one body:

sql
CREATE FUNCTION log_stock() RETURNS trigger LANGUAGE nusascript AS $$
BEGIN
  INSERT INTO stock_log (sku, before, after) VALUES (OLD.sku, OLD.qty, NEW.qty);
END
$$;

CREATE TRIGGER stock_fn AFTER UPDATE ON stock FOR EACH ROW
WHEN (NEW.qty <> OLD.qty) EXECUTE FUNCTION log_stock();

The function must take no parameters and have a BEGIN ... END body; that is checked when the trigger is created, not on first fire. EXECUTE PROCEDURE is a synonym. NEW and OLD are available throughout the body, a RETURN only ends it, and a BEFORE trigger cannot change or skip the row either way. Function arguments in the trigger (EXECUTE FUNCTION f('x')) are not accepted. The action runs in the same transaction as the triggering statement; an error in it aborts that statement. Cascading triggers are bounded by a depth limit (54001).

An INSTEAD OF trigger attaches to a view and replaces the write: an INSERT, UPDATE or DELETE on the view fires the trigger once per row, with NEW as the proposed view row and OLD as the current one, and the trigger's action is the only write. Such triggers take precedence over the auto-updatable view rewrite, are row-level only and take no WHEN condition; RETURNING projects NEW (insert, update) or OLD (delete). BEFORE or AFTER on a view and INSTEAD OF on a table are refused with 42809.

sql
CREATE TABLE items (id INT PRIMARY KEY, v TEXT, hidden BOOLEAN);
CREATE VIEW active AS SELECT id, v FROM items WHERE NOT hidden;
CREATE TRIGGER active_ins INSTEAD OF INSERT ON active
  FOR EACH ROW INSERT INTO items VALUES (NEW.id, NEW.v, false);
INSERT INTO active VALUES (1, 'a');   -- runs the trigger's INSERT instead
SELECT * FROM items;
-- id | v | hidden
-- ---+---+-------
-- 1  | a | false

A NULL in NEW.col or OLD.col has the column's type for a date/time, interval, boolean, numeric, floating-point, UUID, enum, JSON/JSONB or MAC address column, and for a domain over one of these. An integer column's NULL is an INT. Any other column gives an untyped NULL, which takes the type of the expression it meets. The same holds for the row an event does not have (OLD in an INSERT, NEW in a DELETE).

sql
CREATE TABLE task (id INT PRIMARY KEY, due TIMESTAMPTZ);
CREATE TABLE reminder (task_id INT, remind_at TIMESTAMPTZ);
CREATE TRIGGER task_reminder AFTER INSERT ON task FOR EACH ROW
INSERT INTO reminder VALUES (NEW.id, NEW.due - INTERVAL '1 day');

INSERT INTO task VALUES (1, '2026-11-02 09:00+00'), (2, NULL);
SELECT task_id, remind_at FROM reminder ORDER BY task_id;
--  task_id | remind_at
-- ---------+------------------------
--        1 | 2026-11-01 09:00:00+00
--        2 | NULL

Prepared statements and cursors

Prepared statements

Drivers prepare through the wire protocol: a statement is parsed once and run with values for $1..$n.

python
cur.execute("SELECT email FROM customers WHERE country = $1 ORDER BY email", ["ID"])

The SQL spellings work too, on any connection, which is how the shell binds parameters:

sql
PREPARE by_country AS SELECT email FROM customers WHERE country = $1 ORDER BY email;
EXECUTE by_country('ID');
EXECUTE by_country('SG');
DEALLOCATE by_country;       -- or DEALLOCATE ALL

A prepared statement lives for the connection and survives transaction ends. Only a runnable query may be prepared (SELECT, set operation, INSERT, UPDATE, DELETE). Executing an unknown or deallocated name is 26000; the wrong number of arguments is 42883; EXECUTE ... USING is not accepted.

Cursors

A cursor reads a result in pieces. Its rows are captured when the cursor is declared, so it pages through a stable snapshot.

sql
BEGIN;
DECLARE c CURSOR FOR SELECT id, email FROM customers ORDER BY id;
FETCH 2 FROM c;
FETCH NEXT FROM c;
FETCH ALL FROM c;
CLOSE c;
COMMIT;

MOVE takes the same directions as FETCH and positions the cursor exactly as that FETCH would, but returns no rows. Its command tag is MOVE <count>, where the count is the number of rows the FETCH would have returned.

sql
MOVE FORWARD 100 IN c;   -- skip ahead; the tag says how many rows were passed over
MOVE ABSOLUTE 0 IN c;    -- back to before the first row

The directions are NEXT, PRIOR, FIRST, LAST, ABSOLUTE n, RELATIVE n, a bare count n, ALL, FORWARD [n | ALL] and BACKWARD [n | ALL]. With no direction the statement means NEXT, and the FROM or IN before the cursor name may be left out. Every cursor can move in any direction, whether or not it was declared SCROLL.

Counts are signed:

  • ABSOLUTE n goes to the n-th row from the start; a negative n counts from the end, so ABSOLUTE -1 is the last row and ABSOLUTE -2 the one before it. ABSOLUTE 0 goes to before the first row and returns nothing.
  • RELATIVE n moves n rows from the current one, backward when n is negative.
  • A negative count in FETCH n or FORWARD n reads backward, and a negative BACKWARD n reads forward. A count of 0 (and RELATIVE 0) re-reads the current row.
  • Asking for a row before the first or after the last returns nothing and leaves the cursor before the first row or after the last one; the next FETCH NEXT or FETCH PRIOR starts from there. A count that runs off either end returns the rows it found and stops in the same place.

Backward reads return rows nearest first.

A cursor belongs to the transaction that declares it:

  • Without WITH HOLD, the cursor closes when that transaction ends, by COMMIT or ROLLBACK, and fetching from it afterwards is 34000. Such a cursor can only be declared inside BEGIN ... COMMIT; outside a transaction block DECLARE is refused with 25P01.
  • With WITH HOLD, the cursor stays open after its transaction commits, until CLOSE or the end of the session. It may be declared outside a transaction block. If its transaction rolls back, the cursor is closed with it.
sql
DECLARE recent CURSOR WITH HOLD FOR SELECT id FROM orders ORDER BY id DESC;
FETCH 50 FROM recent;
CLOSE recent;

Declaring a name that is already open is refused with 42P03, and the open cursor keeps its rows and position. Fetching from, moving or closing an unknown cursor is 34000.

A DECLARE sent through the extended query protocol may use $n parameters in its query. The bound values are substituted when the cursor is declared, so the rows it returns are fixed then. Over that protocol a FETCH is described with its cursor's columns, and it can be read in pieces with a row limit or in binary result format like any other query.

Transactions and locking

The full model, including what to do on a conflict, is in transactions. The statements:

sql
BEGIN;                                             -- or START TRANSACTION
BEGIN ISOLATION LEVEL SERIALIZABLE;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;   -- before the transaction's first query
SAVEPOINT s1;
ROLLBACK TO SAVEPOINT s1;
RELEASE SAVEPOINT s1;
SET CONSTRAINTS ALL DEFERRED;                      -- see Deferrable constraints
COMMIT;                                            -- or END
ROLLBACK;

SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE;   -- session default

PREPARE TRANSACTION 'gid';      -- two-phase commit: keep the transaction, prepared
COMMIT PREPARED 'gid';          -- from any connection, outside a transaction block
ROLLBACK PREPARED 'gid';

The default isolation level is READ COMMITTED. A statement outside BEGIN runs in its own transaction. After an error inside a transaction, every further statement is refused with 25P02 until ROLLBACK (or ROLLBACK TO SAVEPOINT). Two-phase commit, its error codes and the nusadb_prepared_xacts view are described in transactions.

Several statements sent as one simple query (INSERT ...; UPDATE ...) run as one transaction unless they are already inside one: an error rolls back all of them. A BEGIN among them opens an ordinary transaction block instead. The full rules are under clients. COPY inside a transaction block is part of it and is undone by its ROLLBACK.

DDL is transactional too, and other sessions keep seeing the committed definition of a table until it commits. A write to a table another transaction is altering fails at once with 40001; see schema changes inside a transaction.

Row and table locks

Locks never wait. A row someone else has locked fails immediately with 40001, so NOWAIT is implied; SKIP LOCKED skips such rows instead, which suits a job queue. A held row lock also blocks writers: an UPDATE or DELETE that touches the locked row fails with the same immediate 40001 until the locking transaction ends. With LIMIT n, only the first n rows in query order are locked, so a LIMIT 1 ... SKIP LOCKED claim takes one row and leaves the rest for other workers.

sql
SELECT * FROM orders WHERE id = 1 FOR UPDATE;      -- also on an inheritance parent (locks
                                                   -- matched rows in parent and children)
SELECT * FROM orders ORDER BY id LIMIT 1 FOR UPDATE SKIP LOCKED;   -- claim one job
SELECT * FROM orders FOR UPDATE OF orders NOWAIT;
SELECT * FROM orders FOR SHARE;

LOCK TABLE orders IN ACCESS EXCLUSIVE MODE;        -- inside a transaction
LOCK TABLE orders, customers IN ACCESS SHARE MODE;

LOCK TABLE accepts ACCESS SHARE and ACCESS EXCLUSIVE; the other modes are refused.

Notifications

LISTEN subscribes a connection to a channel; NOTIFY from any connection in the same database delivers to every listener. Inside a transaction the notification is queued and sent at COMMIT (and dropped on ROLLBACK); in autocommit it is sent at once. A listener receives notifications between its own statements, which is how the drivers surface them.

sql
-- session 1
LISTEN orders_changed;

-- session 2
NOTIFY orders_changed, 'order 42 shipped';

-- session 1
UNLISTEN orders_changed;
UNLISTEN *;

Maintenance

sql
ANALYZE customers;        -- refresh planner statistics for one table
ANALYZE;                  -- every table
VACUUM;                   -- reclaim row versions no snapshot can see
VACUUM (FULL, ANALYZE) orders;
REINDEX TABLE orders;     -- rebuild indexes an earlier release built over CHAR columns
CLUSTER orders;           -- accepted for compatibility; rows are already clustered by row id, so it is a no-op
CREATE EXTENSION IF NOT EXISTS vector;   -- accepted for compatibility; installs nothing, every type is built in
CHECKPOINT;               -- fold the log into an image and truncate it; needs a quiet engine

A background worker re-analyzes tables whose statistics have gone stale, so ANALYZE by hand matters mainly right after a large load. Version reclamation also runs in the background; VACUUM triggers it now. CHECKPOINT refuses while any transaction is in flight, including one on the connection that issues it; see checkpoints.

REINDEX {INDEX name | TABLE name | SCHEMA name | DATABASE name | SYSTEM} rebuilds the indexes an earlier release built over CHAR(n) columns and leaves every other index alone. REINDEX INDEX and REINDEX TABLE need the table's owner or a superuser (42501). REINDEX SCHEMA and REINDEX DATABASE rebuild the tables the role owns, commit each table on its own, and are refused inside a transaction block (25001). REINDEX DATABASE must name the current database (0A000). See upgrades.

Volatility

Every built-in function belongs to one of three classes, which decide where it may be used:

ClassMeaningExamples
immutablethe same arguments always give the same resultlower, abs, date_trunc, age(end, start) and most others
stablefixed within a statement or transaction, but not across them or across sessionsthe transaction clock (now(), current_timestamp, current_date, current_time, localtimestamp, localtime, statement_timestamp()), age(value), current_user, session_user, current_setting, current_database, current_schema, version()
volatilemay change on every callclock_timestamp(), random(), setseed(), gen_random_uuid() and uuid_generate_v4(), uuidv7(), nextval, currval, setval, and the advisory-lock functions

An index key expression, a partial-index WHERE predicate and a generated column may call only immutable built-ins; anything else is refused with 42P17. A CHECK constraint, on a table or a domain, may not call a volatile built-in (42P17), but it may call a stable one: CHECK (placed <= now()) is accepted and tests each row against the time of the transaction that writes it. Such a check is not re-run later, so rows already stored stay valid as time moves on. User-defined functions carry no volatility marking and are not checked by these rules. A partition key is stricter: it accepts immutable built-ins only, and no user-defined functions.

These rules apply when an object is created. An index, generated column, CHECK constraint or domain that an earlier release accepted keeps loading and working as before. The error names a function the way it is written: current_user, current_date, localtime and the other keyword forms without parentheses, everything else as random().

Access control

Who may connect, and with which password, is decided by the server's --auth-user list (see authentication and users); SQL roles decide what a connected user may do. Create a role with the same name as each --auth-user entry, then grant it privileges. A user that authenticates but has no role in the catalog can create its own tables and nothing else: reading or changing another role's table needs a grant either way. PASSWORD in CREATE ROLE is refused, because a password set there would never be checked at login.

sql
CREATE ROLE analyst LOGIN;
CREATE USER app;                            -- USER is ROLE with LOGIN on
CREATE ROLE readers;                        -- a group: NOLOGIN by default
ALTER ROLE analyst NOLOGIN;
ALTER ROLE analyst LOGIN;
GRANT readers TO analyst;
REVOKE readers FROM analyst;
GRANT readers TO analyst;

GRANT SELECT ON customers TO readers;
GRANT SELECT (email, country) ON customers TO analyst;   -- column-level
GRANT INSERT, UPDATE ON orders TO analyst WITH GRANT OPTION;
GRANT ALL ON orders TO app;
REVOKE INSERT ON orders FROM analyst;

SET ROLE analyst;                           -- act as that role for the rest of the session
SELECT email FROM customers;                -- allowed through readers
INSERT INTO orders (customer, total) VALUES (1, 5);
-- ERROR 42501: permission denied: INSERT on column `customer` of table `public.orders`
RESET ROLE;

Privileges: SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER, ALL. SELECT, INSERT, UPDATE and REFERENCES may name columns in parentheses. Role attributes: LOGIN / NOLOGIN and SUPERUSER / NOSUPERUSER; the attribute is recorded in nusadb_roles, and grants are what restrict a role. A role that lacks a privilege is refused with 42501, and reading a column outside its column grant is refused the same way even through SELECT *. The bootstrap superuser nusadb-root bypasses every check.

Creating a table, view, materialized view, sequence, function, procedure, type or domain needs CREATE on the schema it lands in. A schema's owner (the role that created it) always has it, and other roles need a grant. Functions, procedures, types, domains and materialized views always live in public. Every role may create in public until that is revoked:

sql
REVOKE CREATE ON SCHEMA public FROM PUBLIC;   -- lock the default schema down
GRANT CREATE ON SCHEMA public TO app;         -- let one role back in
GRANT CREATE ON SCHEMA reporting TO analyst;
CREATE TABLE scratch (id BIGINT);             -- as a role without the grant:
-- ERROR 42501: permission denied: CREATE on schema "public" is required to create objects in it

The revoke is stored in the catalog and survives a restart; GRANT CREATE ON SCHEMA public TO PUBLIC restores the default. Temporary tables need no grant. CREATE INDEX needs ownership of the table and CREATE TRIGGER the TRIGGER privilege on it. CREATE SCHEMA and CREATE DATABASE need the CREATEDB role attribute, over a connection as well as in an embedded session. USAGE on a schema can be granted and revoked but is not checked when a name is looked up.

Row-level security restricts which rows a role sees or may write:

sql
GRANT SELECT, UPDATE ON orders TO analyst;
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

CREATE POLICY own_rows ON orders
  FOR ALL TO analyst
  USING (customer = current_setting('app.customer')::BIGINT)
  WITH CHECK (customer = current_setting('app.customer')::BIGINT);

CREATE POLICY no_refunds ON orders AS RESTRICTIVE FOR UPDATE USING (total >= 0);

ALTER POLICY own_rows ON orders USING (customer = current_setting('app.customer')::BIGINT);
DROP POLICY no_refunds ON orders;

SET app.customer = '1';
SET ROLE analyst;
SELECT id, customer FROM orders;       -- only customer 1's rows
RESET ROLE;

USING filters rows read; WITH CHECK validates rows written (a write that fails it is 42501). Policies are PERMISSIVE by default (any one may allow a row) or RESTRICTIVE (all must allow). Ownership, grants, role membership and policies are enforced inside the engine; a superuser bypasses them.

NusaDB-specific behaviour

The behaviour in this section differs from what many other SQL engines do.

Text ordering and collation

Comparison and ordering are bytewise, equivalent to a C collation. COLLATE "C" and "POSIX" are accepted; locale collations are refused. Byte order is deterministic and does not change when a system library is upgraded, which is what makes an index safe across upgrades. The visible effect is that uppercase sorts before lowercase.

sql
SELECT 'a' < 'B' AS byte_order;   -- false: 'B' (0x42) precedes 'a' (0x61)

Fixed-width characters (CHAR(n))

CHAR(n) is a fixed-width type. A value is stored with its trailing spaces trimmed, so comparison and || treat 'ab' and 'ab ' as equal and length counts only the real characters. A CHAR(n) column read out as a result on its own is blank-padded back to n characters, and octet_length reports that full width. As a key of a PRIMARY KEY, UNIQUE constraint, index or foreign key, trailing blanks are ignored: 'x' and 'x ' are the same key, and inserting both into a CHAR(5) PRIMARY KEY fails with 23505. Indexes built by earlier releases are covered under upgrades.

NUMERIC division precision

Division produces a fixed scale rather than deriving one from the operands. The value is the same; only the number of digits kept differs. Round explicitly when a specific scale matters.

How JSON is stored

JSON and JSONB both store a parsed value, so key order and insignificant whitespace from the input text are not preserved. Keep the original text in a TEXT column when byte fidelity matters, such as a signed payload.

Floating-point text output is canonical

A REAL / DOUBLE PRECISION value renders in the shortest form that reads back to the same number, switching to exponent notation outside 0.0001 .. 10^15 (1e+20, 2.5e-07), and the non-finite values render Infinity, -Infinity and NaN. The same rendering is used in query results, casts to text and array elements, so the three always agree.

Assigning between TIMESTAMP and TIMESTAMPTZ

A value of either type can be assigned to a column of the other and the instant passes through unchanged. The two also compare and unify, the TIMESTAMP side read in the session time zone (see Dates, times and intervals).

Type coercion is explicit

The engine does not insert implicit coercions between unrelated types. Cast explicitly with ::TYPE when mixing them. The exceptions are the numeric widenings, DATE / TIMESTAMP / TIMESTAMPTZ mixing, a quoted literal taking the type it is compared with, and a bare NULL taking the type its operator needs.

SERIAL columns are integer

SERIAL, BIGSERIAL and SMALLSERIAL all report their type as integer. Declare BIGINT GENERATED ALWAYS AS IDENTITY when the key must be a BIGINT, for example because it is compared with a BIGINT column in IN (subquery), which requires both sides to have the same type.

Identifiers fold to lower case

Users and users name the same table; "Users" (double-quoted) keeps its case and is a different name. Identifiers are ASCII letters, digits and _.

Materialized views are snapshots

A materialized view holds the result from the last REFRESH. Incremental maintenance is opt-in with WITH (incremental = true), and asking for it on a body that cannot be maintained incrementally is an error.

Serialization conflicts and the auto-commit retry

Concurrency control is optimistic and locks do not wait: two sessions writing the same row make one fail with SQLSTATE 40001 rather than queue.

A single statement outside a transaction is retried by the server, because it committed nothing and showed the application no intermediate result. Inside BEGIN ... COMMIT it is not, because a statement there may follow others whose results the application already acted on.

sql
SET max_autocommit_retries = 50;   -- 0 turns the retry off

A conflict that outlasts the retry budget is reported unchanged, so an application's own retry loop still sees its 40001. A retry re-runs the statement, so now() and random() produce fresh values and a sequence consumed by a failed attempt leaves a gap. Pair the budget with statement_timeout if you want an upper bound on how long one statement may hold a connection.

Memory budgets and spilling

A sort, DISTINCT, GROUP BY, set operation or hash join whose input exceeds the work-memory budget streams the overflow to the spill directory when one is configured (--spill-dir, or automatically on a Linux host where the budget is detected), and a spilled sort, DISTINCT or GROUP BY streams its result back from there, so the result may be larger than the budget. Without a spill directory, a stage over --work-mem fails with an error naming the limit, the bytes involved and how to raise it, and the server stays responsive. Window functions evaluate each partition in memory when it fits and from disk when it does not; over a partition larger than the budget only a RANGE / GROUPS frame with an offset, or an aggregate frame that has to hold its rows (one with EXCLUDE, a floating-point sum or avg, or array_agg and similar), holding more rows than the budget fails. DISTINCT ON and ROLLUP / CUBE / GROUPING SETS spill as well. SET work_mem moves both the budget and the point where spilling starts.

TABLESAMPLE samples per row

TABLESAMPLE BERNOULLI (n) and SYSTEM (n) keep each row with probability n%, drawn before the WHERE filter runs. Both methods sample per row; SYSTEM does not sample by storage page. The 0% and 100% endpoints return no rows and every row. REPEATABLE (seed) makes the draw deterministic across repeated scans. A percentage outside [0, 100] is 2202H; an unknown method is 42704. Supported on a base table (including an inheritance parent); not on a CTE, view, derived table, or JOIN input.

Capacity and memory

Table and B-tree index pages live in a page cache over the checkpoint image: clean pages are evicted and changed pages spill to a scratch file, so a database can be larger than memory. Index entries too large for an index page stay in memory and count against the resident bound; vector indexes are held in memory whole. See memory limits and capacity.

  • LIST partitioning over several columns, a unique index or an EXCLUDE constraint on a partitioned table, and MERGE into a partitioned table;
  • EXCLUDE constraints with an operator other than = or &&;
  • a foreign key SET DEFAULT action when it runs, and a column list on ON UPDATE SET NULL;
  • SET column = DEFAULT in ON CONFLICT DO UPDATE;
  • a multi-column CYCLE clause, or its TO ... DEFAULT ... marker form;
  • EXECUTE ... USING, and arguments to a trigger function;
  • aggregating a row value with anything but count;
  • dollar-quoted string literals outside a routine body;
  • LOCK TABLE modes other than ACCESS SHARE and ACCESS EXCLUSIVE;
  • SET NAMES, and an IANA region name as the session time zone;
  • locale collations (only "C" / "POSIX");
  • COPY to or from a file or program (only STDIN / STDOUT);
  • BEGIN READ ONLY / SET TRANSACTION READ ONLY over a connection;
  • full-text configurations other than simple, english and indonesian, and full-text prefix matching;
  • IGNORE NULLS / RESPECT NULLS on window functions;
  • storing a multi-dimensional array in a column (a multi-dimensional ARRAY[[1,2],[3,4]] value works inside a query, with array_ndims and [i][j] subscripts);
  • a DEFAULT or COLLATE on a domain;
  • a LANGUAGE other than SQL and NusaScript (LANGUAGE nusascript) for functions and procedures.
