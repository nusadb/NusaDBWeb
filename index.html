Install

Relational SQL on one machine, from the wire protocol down to the 8 KiB page.

One server binary, written in Rust, that keeps rows in the leaves of a clustered B+tree, returns from COMMIT once a checksummed redo log is on disk, and speaks its own wire protocol to drivers in eight languages.

WITH RECURSIVE days(d) AS (
  SELECT DATE '2026-10-01'
  UNION ALL
  SELECT d + 1 FROM days WHERE d < DATE '2026-10-05'

SELECT d AS day,
       coalesce(sum(o.total), 0) AS revenue,

Fit

One server, one disk, one SQL database you can reason about

For applications on a single host that want ordinary relational guarantees from it. It is not a cluster, so the second list matters as much as the first.

Limits and capacity, in full

Fits today

  • An application database on one host, with SERIALIZABLE available per transaction when a race would be expensive.
  • Data larger than memory. Table and index pages are cached, evicted and spilled under --max-resident-bytes.
  • Reporting next to transactions: window functions, recursive CTEs, grouping sets, and sorts, joins and aggregates that spill to disk instead of failing.
  • Search without another service: full-text in the simple, english and indonesian configurations, and VECTOR(n) with an HNSW index.
  • Operators who want encryption at rest, scheduled backups and point-in-time restore from flags on the server binary.

Does not fit yet

  • Failover without a person. There is no clustering. A read-only standby follows the primary and is promoted by restarting it without --standby-from.
  • A standby that must trail by seconds. Log segments reach the archive when the primary checkpoints, so the standby lags by that cadence.
  • Tools that speak another database's protocol. NusaDB has its own; use one of the eight drivers or nusadb-cli.
  • Vector indexes larger than RAM. HNSW graphs are held in memory whatever the page-cache bound.
  • Named time zones and locale collations. SET TIME ZONE takes UTC or a fixed offset, and text compares by bytes.
Write path

A commit is durable at the fsync. A checkpoint folds the log away.

Changed pages stay in the page cache and reach disk only through a checkpoint, which writes just those pages to a new immutable segment. Watch two transactions go through.

Storage

The row is in the leaf. Its history is one pointer away.

Tables are clustered B-link trees keyed by a row id the engine assigns, so a lookup ends at the leaf that holds the row, with no second hop into a separate heap. A reader that arrives during a split follows the right link instead of starting over.

Old versions

An UPDATE moves the old header and tuple into an undo arena and writes the new version into the leaf, pointing back at it. A DELETE stamps xmax in place. A reader whose snapshot cannot see the leaf version walks the chain newest first and takes the first version whose creator it can see.

A rolled-back transaction restores the previous leaf bytes and leaves no versions behind, so visibility needs only the snapshot's set of active transactions, not a commit log. Background purge frees arena slots no snapshot can reach.

Durability

Each log record carries its position, its length and a CRC over both.

The log is the durable copy of every change since the last checkpoint. Because the CRC32 covers the 16-byte header as well as the body, a zeroed sector or a corrupted length is caught, and a torn record at the end of the file ends the durable prefix cleanly.

64 MiBlog size at which the background worker checkpoints a database (--checkpoint-threshold-bytes)
5 show often the worker checks each log (--checkpoint-interval)
2 slongest it holds new transactions to find a quiet moment (--checkpoint-max-pause)
2 passesat recovery: collect the committed transactions, then re-apply only their operations, in log order

Architecture

Seven layers, one dependency direction

The storage side never imports the SQL side. They meet at one Rust trait, so each half can be tested on its own. Storage code is also exercised against simulated disks that tear writes, fail fsync and lose power, replayable from a single seed.

  1. Client

    nusadb-cli with aligned, expanded, CSV and JSON output, drivers for Rust, Java, Node.js, Python, Go, Ruby, PHP and .NET, and a C API.

  2. Protocol

    Length-prefixed frames on one port. TLS 1.3 through rustls, mutual TLS with --tls-client-ca, SCRAM-SHA-256, extended query with named statements and portals, COPY in text and binary, notices.

  3. SQL engine

    Parser, analyzer, a cost-based planner that reads histograms and most-common values, and a vectorized executor working on 1,024-row batches with AVX2 kernels and a portable fallback.

  4. Transactions

    Snapshots from version stamps, no-wait row locks, serializable snapshot isolation tracked per row, savepoints, two-phase commit, deferrable constraints.

  5. Storage

    Clustered B-link tables, B+tree indexes in pages too, a page cache with clock eviction and spill, HNSW graphs for vectors, and a background purge of dead versions.

  6. Log

    Redo records with CRC32 and lz4, optionally sealed, a commit that returns after fsync, incremental checkpoints over immutable segments, and an optional archive for point-in-time restore.

  7. Files

    One directory per database under base/, a cluster catalog under global/, and a lock file that keeps a second server off the same directory.

FAQ

Questions people ask first

Can I connect with a client written for another database?

No. NusaDB has its own wire protocol, and a client that sends another engine's handshake gets no answer, so it looks like a connection that hangs. Use nusadb-cli, one of the eight drivers, or write a client against the protocol specification. SQL written for other engines usually runs unchanged.

What happens on a crash?

Every transaction whose COMMIT returned is there after restart, and nothing of one that had not. The engine opens the last checkpoint image, loads pages from its segments as they are used, and replays the log written after it. Restart time grows with the log written since the last checkpoint, not with the size of the data.

Why did my transaction fail with 40001?

Locks do not wait. When two transactions write the same row, or a serializable transaction would see a result no serial order could produce, one of them fails with 40001 and should be retried. A single autocommit statement is retried by the server, up to max_autocommit_retries attempts (50 by default). Explicit transactions need a retry loop in the application; the transactions page has one in several languages.

Does my data have to fit in memory?

Table pages and B-tree index pages do not. They are loaded from segments on first use, evicted when clean and spilled when changed. Index entries larger than about 2 KB, notes for index entries awaiting purge, and HNSW vector graphs stay in memory. When those reach the bound, the next insert or update fails with an out-of-memory error rather than the process growing until the host kills it.

How do I back up a running server?

A checkpoint image with the segments it names is a consistent copy of one database, taken while the server keeps writing. --backup-dir takes hard-link snapshots of them on a schedule. For point-in-time restore, add --wal-archive-dir and rebuild offline with --restore-database and --restore-to-time. Copying backups off the machine is up to you.

Is it ready for production?

It is a pre-1.0 beta. The storage format is versioned and a newer release upgrades an older data directory in place, but interfaces can still change between releases, and the features on the limits page are not built. Read that page before deciding.

Which SQL does it accept?

Most of standard SQL that makes sense on one node: joins of every kind, subqueries, CTEs including recursive ones, window functions, grouping sets, MERGE, ON CONFLICT, triggers, SQL and NusaScript routines, views and materialized views, partitioned tables, sequences, and a wide type system. The statement index lists each statement with an example, and not accepted lists what is refused.
