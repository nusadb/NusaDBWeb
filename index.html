A relational database engine, written from scratch in Rust.

NusaDB runs on one node and handles transactional and analytical work in the same engine. Rows live in a clustered B+tree, transactions use multi-version concurrency control, and every commit goes through a write-ahead log before it is acknowledged.

nusa-cli 
-- one connection, one database
CREATE TABLE orders (
  id     BIGINT PRIMARY KEY,
  region TEXT   NOT NULL,
  total  NUMERIC(12,2),
  placed TIMESTAMPTZ DEFAULT now()
);

SELECT region,
       count(*)          AS n,
       sum(total)        AS revenue,
       rank() OVER (ORDER BY sum(total) DESC)
FROM   orders
WHERE  placed >= now() - INTERVAL '30 days'
GROUP BY region
HAVING sum(total) > 1000;

 west   |  980 |  97015.20 |    2

What the engine does today

Everything below is implemented and covered by tests in the repository. Features that are planned but not built are listed on the limits page instead of here.

transactions

MVCC and snapshot isolation

Readers never block writers. All four standard isolation levels are available, up to serializable snapshot isolation, with savepoints and partial rollback.

storage

Clustered B+tree

Rows are stored in the leaves of a B-link/B+tree keyed by an engine-minted row id, so a primary-key lookup reaches the row without a second fetch.

durability

Write-ahead log

Each record carries a CRC32 and is lz4-compressed. A commit is acknowledged only after its log record is durable; recovery replays the log on start.

queries

Cost-based planner

Histograms and most-common-value statistics drive join ordering and index selection. Plans run through a vectorized executor in batches rather than row at a time.

sql

A broad SQL surface

Window functions, recursive CTEs, set operations, lateral joins, grouping sets, MERGE, ON CONFLICT, views, materialized views, sequences, domains and triggers.

security

Authentication and access control

SCRAM-SHA-256 over optional TLS, including mutual TLS. Roles, GRANT/REVOKE and row-level security policies are enforced inside the engine.

It speaks its own protocol

This is the first thing to know before you plan an integration.

NusaDB does not implement another database's wire format. A client built for a different engine will not connect at all — the server does not answer a handshake it does not recognise, which from the client side looks like a dead socket. That is deliberate rather than unfinished.

The SQL dialect is a separate question. Queries written for other engines generally run unchanged once they arrive over a NusaDB connection. Use nusa-cli, one of the official drivers, or write a client against the protocol specification.

  • Default port 5678
  • Clients nusa-cli, Rust, Java, Node, Python, Go, Ruby, PHP, .NET
  • Authentication SCRAM-SHA-256, optional mutual TLS
  • Bulk transfer COPY … FROM STDIN / TO STDOUT
  • Observability Prometheus endpoint
  • Deployment Single binary, or the published container image

Start in about a minute

The container image needs no build step. Building from source needs a Rust toolchain.

Container

shell
docker run -d --name nusadb \
  -p 5678:5678 \
  -v nusadb-data:/var/lib/nusadb \
  -e NUSADB_USER=app \
  -e NUSADB_PASSWORD=change-me \
  nusadb/nusadb:0.1.0-beta.8

docker exec -it nusadb nusa-cli \
  --user app --database nusadb

From source

shell
git clone https://github.com/nusadb/nusadb.git
cd nusadb
cargo build --release

./target/release/nusadb-server \
  --listen 127.0.0.1:5678 \
  --data-dir ./data

./target/release/nusa-cli \
  --host 127.0.0.1:5678 --user nusa-root

With no credentials configured the server accepts every client without a password and says so in its startup log. Fine on a laptop; set --auth-user before anything else. Full walkthrough in getting started.

Before you put data in it

NusaDB is pre-1.0 and there are limits worth knowing in advance rather than discovering during a load. These are the ones that change how you size a deployment.

Working data must fit in memory

Table pages are held in memory and are not evicted to disk. Past the resident ceiling, inserts are refused with an error naming the limit. A dataset larger than memory does not fit — it is not merely slower.

The log is the durable copy

No checkpoint truncates the write-ahead log yet, so the data directory grows with write history rather than with live data.

Restart replays the log

Because recovery reads that history, start-up time grows with it. Plan restart windows around log size, not table size.
